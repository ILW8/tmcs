# Milestone 1 soak results

Soaks run on 2026-10-24 on the owner's PC (Ryzen 9 7950X, Windows 10 Pro 19045), at commit 2902cc7.

## Setup

- **Churn:** `tools/churn.ps1 -Parallel 8 -Minutes 52`, 15:36Z to 16:28Z. It spawned 23,472 `cmd /c ping` processes, about 450 a minute, plus their `ping` and `conhost` children. Both soaks share it (ruling R54).
- **Elevated soak:** the published Release build `artifacts/publish/tmcs.exe`, run elevated (one UAC prompt).
  - Scenario: `details:10,minimized:10,details:3,paused:5,details:2`.
  - Ran 15:40:42Z to 16:10:32Z: 181 rows.
- **Non-elevated soak:** the Debug build of the same commit.
  - Scenario: `details:10,minimized:30,details:3,paused:5,details:2`.
  - Ran 15:36:40Z to 16:26:30Z: 300 rows.
- **Logging:** each tmcs logs itself every 10 s through `TMCS_DIAG`, and `tools/soak-report.ps1` scores the CSV.
- **Comparison run:** the stock Task Manager ran for part of that window (see Idle cost).

## Verdict

- **Churn soak (spec test 1): no leak.** Both runs FAIL segment 1, and the owner accepted both FAILs as explained:
  - Private bytes (both runs): the garbage collector committing its heap in the first 12 minutes.
  - USER range (Debug run only): a one-time step when the owner focused the window.
  - After each of these, every memory, handle, GDI and USER check is flat for the rest of both runs.
- **Pause:** sampling stops (`samples` delta 0 in both runs).
- **Idle cost (spec test 4):** PASS. tmcs used 4,517 ms of CPU a minute against Task Manager's 9,024 ms.
- **Fidelity (spec test 6):** accepted. The owner's verdict: "looks good at a glance".

## The private-bytes FAIL is the GC committing its heap, not a leak

**What the check saw.** Segment 1 has 48 rows after the warm-up, scored in quarters of 12. The highest private bytes in minutes 2.0–3.8 is 36.57 MB, and in minutes 8.0–9.8 it is 41.55 MB. The difference, 4.98 MB, is the FAIL. The Debug run's segment 1 fails the same way, with 4.73 MB.

**Evidence.**

1. **Before the first garbage collection, private bytes rise with the managed heap, step for step.** Over the first 5.3 minutes:
   - Elevated: private bytes +15.0 MB, managed heap +13.2 MB.
   - Debug: private bytes +13.9 MB, managed heap +13.4 MB.
2. **Private bytes stop rising once the GC reuses memory it already committed.** The table lists each gen0 collection, found where `managed_bytes` drops:

   | Run | Minute | Step | Managed before → after | Private bytes |
   |---|---|---|---|---|
   | elevated | 5.5 | details | 19.21 → 3.33 MB | 41.46 MB |
   | elevated | 12.0 | minimized | 18.95 → 3.30 MB | 46.36 MB |
   | elevated | 18.5 | minimized | 18.80 → 3.26 MB | 46.26 MB |
   | debug | 5.5 | details | 19.41 → 3.48 MB | 39.10 MB |
   | debug | 11.8 | minimized | 18.84 → 3.24 MB | 43.12 MB |
   | debug | 18.5 | minimized | 19.07 → 3.53 MB | 43.07 MB |
   | debug | 25.0 | minimized | 18.93 → 3.34 MB | 43.07 MB |
   | debug | 31.7 | minimized | 19.21 → 3.64 MB | 43.06 MB |

   The managed heap left after each collection stays at 3.2–3.6 MB, so nothing piles up on the managed side.
   - After the second collection (about minute 12), private bytes stay within 0.1 MB for the rest of each run:
     - Elevated: 46.26–46.36 MB over 18 minutes.
     - Debug: 43.00–43.12 MB over more than 22 minutes.
   - Both ranges include the paused and later details segments.
   - Handles, GDI and USER counts stay flat in every segment.
3. **Painting no longer allocates; sampling does.** The managed heap grows 2.46 MB/min on Details and 2.44 MB/min minimized, but only 0.14 MB/min when paused. So the Details list doesn't allocate when it paints (Task 12b). The allocation comes from sampling a churning process list.

**Cause.**
- tmcs uses the workstation, non-concurrent garbage collector (`ConcurrentGarbageCollection` is false in `Tmcs.csproj`).
- On this machine its gen0 budget is about 19 MB: each collection happens when the managed heap reaches that size.
- At 2.45 MB/min, one gen0 cycle takes about 6.5 minutes. The GC finishes committing its memory over the first two cycles, about 12 minutes.
- The 2-minute warm-up in the spec and in `soak-report.ps1` covers less than one cycle.
- Allocating less would make each cycle longer, so the warm-up would get longer, not go away.

**Re-scored with a longer warm-up.** With `-WarmupMinutes 6`, each CSV scores 14 PASS, 0 FAIL, 12 SKIP. The elevated segment 1 then grows 0.14 MB and segment 2 grows 0.01 MB. The SKIPs are the segments shorter than 6 minutes.

**Ruling (owner, 2026-10-24):** the results are accepted as they are, with no re-score and no re-run: "I'm happy with these results, don't think there's a need for a re-score/re-run". The 2-minute reports above stay the record of the run, and the 6-minute scores are context only.

## The non-elevated USER-range FAIL is a single step: the owner focused the window

**What the check saw.** In the Debug run's segment 1, USER objects were 33 for the first three minutes. At 15:39:40Z they were 41, along with handles 460 → 487 and GDI 67 → 68. They peaked at 44 by minute 5. The range, 11, is the FAIL.

**Evidence.**
- **It is one jump between two consecutive samples, 10 s apart, not a climb.**
- **It happened when the owner focused the window and then minimized it.** The owner confirmed doing this around 15:40Z, between the declined UAC prompt (15:37:58Z) and the accepted one (about 15:40:35Z).
  - The scenario shows the window at the bottom of the z-order and never activates it. So this was the window's first activation, which creates the thread's text-input (TSF/IME) windows and handles once. That fits the size of the step.
  - From 15:39:40Z to 15:40:30Z, tmcs used 225 ms of CPU a minute. Before that it used about 4,400 ms a minute; minimized in the scenario, it uses 424 ms a minute.
  - Meanwhile `samples` kept rising once a second, so sampling ran but the list didn't refresh or paint.
- **It never happens again.**
  - For the remaining 47 minutes, USER objects stay between 39 and 44, set by the state: 42–44 on Details, 41 minimized, 39 paused.
  - Every later segment scores a USER range of 0.
  - The elevated run started after the event. It shows the same shape one higher (43–44 Details, 42 minimized, 40 paused), and a USER range of at most 1 in every segment.
- **Handles stay within 460–500 over the whole run.**

**Re-scored with `-WarmupMinutes 6`.** The Debug CSV scores 14 PASS, 0 FAIL, 12 SKIP.

## Icon store

- During the elevated run, `icon_slots` rose from 197 to 229 and `icon_pooled` from 1 to 36. This is not the stock Task Manager's leak.
- In every row of both CSVs, slots = live + pooled + 1, where the 1 is the generic icon.
- The pool of released icons is capped at 64 (`IconStore`'s `releasedPoolCapacity`), and evicted slots are reused. So the image list stays at or below live + 65 slots, about 1 KB each.
- The rise is that capped pool filling with the icons of processes that exited.

## Idle cost (spec test 4)

Everything below was measured during the churn, with both tmcs instances running.

| Process | Window | CPU time | Rate |
|---|---|---|---|
| Task Manager, Details tab, Normal speed | 15:41:43Z–15:46:43Z (5.00 min) | 45,156.2 ms | 9,024 ms/min |
| tmcs elevated, same window | 15:41:52Z–15:46:42Z (4.83 min) | 22,125.0 ms | 4,578 ms/min |
| tmcs elevated, all three details segments | 14.5 min | 65,500.0 ms | 4,517 ms/min |

**Result:** on the Details tab, tmcs uses about half of Task Manager's CPU. PASS. Milestone 1 has only the Details tab.

Other states (elevated):
- Minimized: 138 ms/min.
- Paused: 6.5 ms/min.

Task Manager's 5-minute total and tmcs's segment-1 total (9.8 minutes) are both exactly 45,156.2 ms. That is a coincidence (both are 2,890 ticks of 15.625 ms), not a copy error. Over Task Manager's own window, tmcs used 22,125.0 ms.
